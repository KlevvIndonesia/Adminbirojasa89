## 7. Backend Error Standardization & Safety Audit

Audit pada layer API Express menghasilkan temuan konkret mengenai struktur respons error dan batasan redaksi antara mode *development* dan *production*:

1. **Amplop Error Terstruktur — [`errorHandler.ts`](file:///d:/Admin/adminsunbirojasa/server/src/middleware/errorHandler.ts#L10-L107):**
   - Seluruh `ApiError` dan error middleware dikembalikan dalam format seragam:
     `{ success: false, error: { code, message, field?, retryAfterSeconds?, details? }, timestamp }` (`#L94-L106`).
   - `ApiError` menyimpan properti `field` dan `retryAfterSeconds` secara top-level maupun dari `details` (`#L30-L33`, `#L86-L92`), memudahkan frontend menyematkan badge kolom atau hitungan mundur `Retry-After`.
2. **Catatan Keamanan Development vs Production (`#L53-L84`):**
   - Pada `CONFIG.NODE_ENV === "production"`, `errorHandler` secara ketat me-redact error `>= 500` menjadi `"Terjadi kesalahan internal pada server."` dan memfilter pola `sqlite`, `sql logic error`, `no such column/table`, path Windows/Unix, serta frame stack trace, sekaligus menyembunyikan properti `details`.
   - **Caveat Dev/Sandbox:** Pada `NODE_ENV !== "production"` (termasuk local dev & sandbox), backend tetap memancarkan pesan `err.message` asli dan `details` untuk debugging. Oleh sebab itu, pertahanan akhir agar pengguna UI **tetap terlindung** di semua environment ditopang oleh [`sanitizeActionMessage`](file:///d:/Admin/adminsunbirojasa/src/app/utils/actionErrorClassifier.ts#L83-L134), masking `status >= 500` di [`parseApiErrorResponse`](file:///d:/Admin/adminsunbirojasa/src/app/utils/actionErrorClassifier.ts#L283-L287), dan [`sanitizeBackendMessage`](file:///d:/Admin/adminsunbirojasa/src/app/components/finance/MutationFeedbackDialog.tsx#L29-L31).
3. **Enforcement Route & Controller — [`orderController.ts`](file:///d:/Admin/adminsunbirojasa/server/src/controllers/orderController.ts) & [`orderRoutes.ts`](file:///d:/Admin/adminsunbirojasa/server/src/routes/orderRoutes.ts):**
   - **Order Create (`POST /api/orders`):** Mengonsumsi header `X-Idempotency-Key` atau `body.clientRequestId` via `orderService.createOrderWithIdempotency`, mengembalikan `201` (baru) atau `200` (replay idempoten).
   - **Order Update (`PUT /api/orders/:orderNo`):** Dilindungi `validateOrderUpdatePayload` dan aturan `assertNoProtectedFieldViolations` (menolak `403 PROTECTED_FIELD_VIOLATION` bila klien memodifikasi field pembayaran/verifikasi/biaya yang dikunci). Bug echo nested `payment` dari `financeStore` berhasil dicegah di sisi klien lewat `ApiOrderProvider.sanitizeUpdatesForPut` (`#L416-L464`) + `financeStore.ts` (`#L1873-L1875`).
   - **Stage Transitions (`POST .../advance`, `.../verify-payment`, `.../approve-documents`, `DELETE ...`):** Dijaga `requireAuth`, `requireRoles`, `requireStageAuthority`, pengecekan SVP khusus Stage 6 (`403 FORBIDDEN` di `orderController.ts#L190-L193`), kewajiban bukti bayar (`422 PAYMENT_PROOF_REQUIRED`), konflik stage (`409 CONFLICT`), dan hard delete role lock.
